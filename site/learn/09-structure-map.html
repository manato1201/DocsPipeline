機械の地図 (docspipeline map)¶

目的¶

ソースを読んで 依存の地図を機械的に作り、(1) アーキテクチャ文書の下書き、(2) 依存の向きの点検、 (3) 手書きの構成図とのずれの検出、に使う。

設計書の追補 (Z16: oh-my-mermaid、X3: Graphify) の考え方を、自前の部品として実装したもの。外部のツールは使わず、 コードの情報を外部へ送らない (ローカルで読むだけ)。

docspipeline map (毎回作り直せる)

直さない。コードを直す

理由

なぜその依存があるのか、どう読めばよいか

人が書く (コードの読み方・設計)

人が書く。地図とのずれは、テストで検出する

使い方¶

docspipeline map docspipeline                       # Markdown の下書き (標準出力)
docspipeline map docspipeline -o /tmp/draft.md      # ファイルへ
docspipeline map docspipeline --format mermaid      # 図だけ
docspipeline map docspipeline --format json         # 機械で読む用
docspipeline map docspipeline --fail-on-cycle       # import の循環があれば、終了コード 1

Markdown の下書きには、依存の図 (Mermaid)、モジュール一覧 (要約・行数・公開 API の数・使う/使われる)、 循環と「どこからも使われていない」モジュール、読み取れないこと が入る。冒頭に「自動生成の下書き。 人が確認してから使い、そのまま公開しない」という警告が付く。

実例: この地図で見つかった不備¶

doctor コマンドを足したとき、mmdc の探索関数を mermaid.py から import した。ところが mermaid.py は Sphinx の拡張で、先頭で docutils を import する。結果、Sphinx が入っていない環境で、docspipeline の どのコマンドも起動時にクラッシュ した (cli → doctor → mermaid → docutils)。

テストは Sphinx が入った環境で走っていたので、気付けなかった。依存の地図を見て分かり、次のように直した。

  1. Sphinx に依存しない部分を docspipeline/mmdc.py に分けた。拡張 (mermaid.py) と doctor.py が、そこから使う。

  2. 再発しないよう、テストにした (下の「ルール」)。

教訓: 「動く環境」でしかテストしていないと、依存の向きの誤りは見えない。地図は、環境に依らずに、構造そのものを検査できる。

ルール (tests/test_structure_map.py)¶

ルール

なぜ

import に循環が無い

循環があると、読む順序が定まらず、import の時点で壊れやすい

Sphinx / docutils を import してよいのは、拡張 (guard・mermaid・doxygen) だけ

core の CLI を、Sphinx なしで動かすため

confluence・diagrams・docstring_coverage・mmdc・scaffold は、他の内部モジュールを import しない (葉)

単体で試せる部品にするため

cli は config・拡張を import しない

CLI は Sphinx を 子プロセス として起動する。同じプロセスに引き込まない

Sphinx を隠した状態で、core が import できる (実行して確かめる)

地図の読み取りに頼らない、最後の砦

手書きの図との突き合わせ¶

module-map の矢印は、tools/diagrams/build_diagrams.py の MODULE_IMPORTS / MODULE_REFERENCES から作る。tests/test_diagrams.py が、同じ読み取り で作った実際の依存と 突き合わせ、次を検出する。

  • 図にあるのに、実際には無い依存 (古くなった矢印)

  • 実際にあるのに、図に無い依存 (描き忘れ。cli → structure_map が、実際にこれで見つかった)

新しい依存を足したら、テストが落ちる。MODULE_IMPORTS に矢印の経路を足し、図を作り直す (拡張のしかた のレシピ 4)。

使うときの注意¶

  • 下書きは、そのまま公開しない。「なぜ」は載っていない。人が確認し、理由を書き足してから使う。

  • 見つけられないもの: importlib.import_module(変数) のような動的な読み込み、組み立てた名前。文字列の参照は、完全一致だけ。

  • 対象は Python のみ。C++ の #include の地図は、実装していない。

  • Graphify との比較は、未実施 (導入していない)。比べるなら、導入前に SKILL.md と監査結果を読む。

よくある誤り¶

  • 地図を コミットする。コードから毎回作れるものを置くと、古くなる。残すのは、人が書いた説明と、テスト。

  • 「循環が無い」ことを、図で目視して済ませる。--fail-on-cycle かテストに任せる。

  • 関数の中の import や、if TYPE_CHECKING: の中の import を、循環として数える。前者は循環を断つ定番の書き方で、 後者は型検査のときだけ。どちらも、実行時の循環ではないので、循環の検出の対象にしない (TYPE_CHECKING の中は、依存としても数えない)。

  • reference を import と同じ強さで扱う。reference は名前の一致だけで、実際に読み込まれるかは分からない。

演習¶

  1. docspipeline map の出力に、外部ライブラリ (module.external) の一覧の列を足す。Sphinx を使うモジュールが、一目で分かるようになる。

  2. 「cli は config を import しない」のような 禁止の依存 を、テストの中のリストではなく、設定ファイル (TOML) で宣言できるようにする。

  3. C++ の #include の地図を作る (C++ の文書)。何を「モジュール」とし、どこまでを内部とするか、先に設計を書く。
