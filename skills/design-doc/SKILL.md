# 設計書のひな形 (契約つき)

DocsPipeline の設計書の書き方を、そのまま使える形にしたもの。形式 (`SKILL.md` + スクリプト + 資料のフォルダ) だけを
参考にした自前のスキルで、外部のコード・文章は含まない。

## いつ使うか

* 新しい機能・モジュールの設計書を書くとき。
* AI に実装を頼む前に、**指示文** (契約) を書くとき。契約は、そのまま実装の指示とテストの種になる。
* 設計書のレビューで、**どこを深く読むか** を決めるとき。

## 手順

1. **ひな形を写す**: [template.md](template.md) を、設計書の置き場所に写す。`〈…〉` の所を、すべて書き換える。
2. **範囲を決める**: 「目的」と「やらないこと」を先に書く。やらないことを書かないと、範囲が広がる。
3. **層を決める**: 主な関数ごとに、層を 1 つ選ぶ。純粋にできるものは純粋にする (引数で受けて、結果を返す)。外の世界に触れる部分だけを、薄い外側に置く。

   | 層 | 触れてよいもの | 触れないもの |
   |---|---|---|
   | 純粋 | 引数だけ | ファイル・環境変数・子プロセス・ネットワーク |
   | 読み取り | ファイルの読み取り・ディレクトリの列挙 | 書き込み・子プロセス・ネットワーク |
   | 書き込み・起動 | ファイルの書き込み・子プロセス | (制限なし。ただし安全の約束を守る) |

4. **契約を書く**: 表の 1 行が 1 つの関数。三つの欄を、**空にしない** (ないときは「なし」と書き、理由を添える)。

   | 欄 | 書くこと |
   |---|---|
   | 事前条件 | 呼ぶ側が守ること。破ったら、**黙って直さず例外で止まる** |
   | 事後条件 | 関数が約束する結果 |
   | 不変条件 | 入力や環境が変わっても **常に** 成り立つこと。実装のコピーではなく、**結果の性質** (冪等・整列済み・値が残らない) で書く |

5. **検証するテストを対応づける**: 各行に、テストの名前を書く。不変条件は、1 つの例ではなく **いろいろな入力** で確かめる。
6. **読む範囲を書く**: 純粋な層は「仕様 (契約) を読めば足りる」、書き込み・起動の層と、秘密を扱う部分は「実装を深く読む」。
7. **検査する**: `python scripts/check_design_doc.py 設計書.md`。見出し・契約の表・層の名前・書き換え忘れを確かめる (終了コード 0 で合格)。

## 自動生成した図・下書きには「札」を付ける

ツールが作った図や一覧は、辺や項目ごとに **出どころ** を区別して見せる。

| 札 | 意味 | 例 |
|---|---|---|
| `EXTRACTED` (読んだ) | 原文に **明示されている** ことを、そのまま読み取った | `import` 文による依存 |
| `INFERRED` (推測した) | 書き方から **推し量った** こと。外れることがある | モジュール名と一致する文字列による参照 |

* 推測を、読んだことのように見せない。人が確認してから使い、そのまま公開しない。
* `docspipeline map` は、依存の辺にこの札を付けて出す。

## 注意

* **企業のコードや、外部の資料の文章を写さない**。構造と考え方だけを取り入れる。
* 契約を変えるときは、**表とテストを同じ変更で直す**。
* 検査が通っても、内容が正しいとは限らない。検査は、書き忘れを見つけるだけ。

## 資料

* [scripts/check_design_doc.py](scripts/check_design_doc.py): 設計書の検査 (標準ライブラリだけ)。
